# Навык: ИБ-01 — разграничение доступа к административному функционалу

## Что считается административным функционалом
По ТС 1.12: управление пользователями, ролями и назначениями очередей, сброс паролей, переименование очередей, выгрузка справочника пользователей. Сюда же — любой API, выполняющий эти действия (например, изменение очереди через JSON).

## Что проверить
1. Построй перечень всех маршрутов (urls.py + include) и отметь административные по назначению, а не по имени.
2. Для каждого найди фактическую серверную проверку: декоратор в urls.py, декоратор функции, проверку в теле до чтения/изменения данных. Раскрой тело каждого guard-декоратора до конца цепочки вызовов.
3. Проверка должна опираться на бизнес-роль `role == 'administrator'` (ТС 4.3.2). `is_staff`, `is_superuser`, членство в группах, `login_required` — НЕ роль. Выясни, кому в проекте выставляется `is_staff` (создание пользователя, смена роли, сидеры): если операторам — такой guard пропускает операторов.
4. Проверь встроенную админку Django (`django.contrib.admin`, `admin.site.urls`).
5. Скрытие ссылок в шаблонах (`{% if user.role ... %}`) не является защитой — смотри только сервер.

## Типичные нарушения
- guard проверяет `request.user.is_staff` вместо роли;
- API/JSON-вариант административной операции защищён только `login_required`;
- проверка роли выполняется после изменения данных или только в шаблоне.

## Не является нарушением
- оператор работает с обращениями назначенных ему очередей (это его права по матрице ТС 4.3.6);
- смена СОБСТВЕННОГО пароля любым вошедшим пользователем;
- библиотечные представления `src/helpdesk`, не подключённые к urls.py проекта (ТС 4.1.5).
