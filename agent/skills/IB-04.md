# Навык: ИБ-04 — криптографическая защита персональных данных при хранении

## Пароли
1. Первый элемент `PASSWORD_HASHERS` — Argon2/BCrypt/Scrypt (или класс-наследник). Раскрой собственный класс хешера: базовый класс и параметры стоимости (time_cost, memory_cost, rounds, work_factor) должны быть заданы явно (ТС 4.5.2).
2. Все пути записи пароля — `set_password`/`make_password`/`create_user`; прямое присваивание `user.password = ...`, `objects.create(password=...)`, фикстуры с открытыми паролями — нарушение. Проверь сидеры и команды management.
3. Не заявляй нарушением: логины/пароли учебных учётных записей в README (это документация стенда) — при необходимости отметь в spec_gaps.

## Прочие ПД (ФИО, логин, e-mail)
1. По ТС 4.5.3 структурированные поля ПД шифруются аутентифицированным шифрованием с ключом ≥ 256 бит. Обычные `CharField/EmailField` модели пользователя без шифрующего типа поля/шифрованной СУБД = хранение в открытом виде. Ограничение прав на файл БД и маскирование не заменяют шифрование.
2. Вложения: шифрование AEAD с уникальным nonce на каждый файл (проверь модуль хранения); ключ хранится отдельно от данных.
3. Проверь длину ключа: срез `[:32]` от 64-байтного ключа — 256 бит, это допустимо.

## Не является нарушением
- хеш пароля в поле `password` модели (он и должен там быть);
- копии e-mail в обращениях — отметь как spec_gaps (data-handling-detail), не как основное нарушение, если модель пользователя уже учтена.
