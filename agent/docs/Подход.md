# Описание подхода — агент проверки требований ИБ (otcysquad, v1.0.1)

## 1. Архитектура и модель

Агент — консольное приложение на Python (только стандартная библиотека), запускаемое отдельным шагом GitHub Actions по push-событию. Пять модулей по ТЗ 4.2:

| Модуль ТЗ | Реализация | Что делает |
|---|---|---|
| Интеграция с CI/CD | `main.py`, `.github/workflows/ib-check.yml` | параметры, дедлайн, публикация артефакта при любом исходе, журнал шага, код 0/1/2 |
| Сбор контекста | `indexer.py` | статический индекс ВСЕГО проекта без его запуска: инвентарь файлов, маршруты с декораторами и телами guard-функций, модели и поля ПД, настройки Django, сигналы аудита, пакетные операции ORM, токены, права доступа к файлам, конфигурация транспорта, ссылки на нормативку в README и docx |
| Анализ | `rules.py` + `analyzer.py` | детерминированные правила по каждому требованию, затем один вызов модели на требование |
| Отчёт | `report.py` | JSON + Markdown по ТЗ 4.6, удаление секретов |
| Принятие решения | `main.py` | код завершения строго по составу нарушений; общий результат отчёта совпадает с кодом |

Модель: DeepSeek (`deepseek-v4-pro`, по умолчанию) или Qwen (`qwen-plus`) через OpenAI-совместимый API; выбор — переменными окружения, без изменения кода; другие провайдеры агент отклоняет (организатор допускает только DeepSeek и Qwen). Режим рассуждений DeepSeek выключен (`thinking: disabled`): в нём рассуждения расходуют тот же лимит ответа и игнорируют `temperature`; без него действует `temperature = 0`, ответ — строго JSON по схеме.

**Проверено на живой модели:** итоговый прогон GitHub Actions [36042637087](https://github.com/zxaty/KMG-Digital-Hackathon-otcysquad/actions/runs/36042637087) на коммите `4459ed1` с `deepseek-v4-pro` — 7 вызовов, 112 950 токенов, 32 с, код 1, 25 нарушений. Все 7 ответов модели пригодны (`finish_reason=stop`), повторов нет. Все 18 находок правил остались в отчёте (12 модель подтвердила — источник `rule+llm`, ни одну не сняла), модель добавила 7 собственных нарушений — все с file:line из переданного контекста, отклонённых проверкой из п. 2.4 — 0. Предыдущий прогон (36037967344, коммит `0fba3c1`, режим рассуждений включён) выявил сбой: по ИБ-04 модель вернула пустой ответ, и требование молча осталось только за правилами; исправление описано в п. 4. Разброс результатов модели между прогонами отдельно не измерялся. Кроме живых прогонов путь с моделью покрыт тестами с локальным фейковым OpenAI-совместимым сервером (повторы при 429/5xx, недоступность → код 2, пустой/обрезанный ответ, нераспознанный статус, дедлайн).

## 2. Методы анализа

1. **Статический анализ (AST).** Разбор urls.py с цепочками include, раскрытие обёрток `login_required(view)` в urls и декораторов у функции, транзитивное раскрытие тел guard-функций (`manage_required` → проверяет `is_staff`, а не роль). Модели и типы полей, `PASSWORD_HASHERS` с раскрытием собственного класса хешера, подключения сигналов в `apps.py` и фильтры обработчиков.
2. **Правила по шаблонам и конфигурации** (`rules.py`): флаги Secure/HSTS/redirect, оценка каждого шифронабора OpenSSL (ECDHE + AEAD — стойкий; RSA-обмен, CBC, SHA-1 — слабый), `http_redirect` транспортного модуля, маршруты без проверки сессии/токена, проверка срока действия токена, выгрузки ПД без роли или аудита, права на каталоги журнала и расположение ключа, покрытие журнала операциями чтения, отказами и событиями СУБД, пакетные `QuerySet.update()` в обход сигналов.
3. **LLM-анализ по требованию.** Модели передаются: текст требования и пункты ТС; **навык проверки** (`skills/IB-0N.md` — методика, типичные нарушения и то, что нарушением НЕ является); находки правил как установленные факты; структурированные данные индекса; **реальные исходники** релевантных файлов с номерами строк; карта всех файлов проекта. Модель подтверждает или оспаривает находки правил, ищет то, что правилам недоступно (логические обходы, неполное покрытие), и отдельно — несоответствия ТС.
4. **Проверка ответа модели.** Каждое нарушение модели обязано указывать file:line из переданных данных; иначе отклоняется как галлюцинация (фиксируется в ограничениях). Фрагмент кода в отчёте всегда берётся из файла, а не из ответа модели. Оспорить находку правила модель может только с контрдоказательством (реальная строка), и только «вероятную» — «подтверждённые» факты конфигурации не снимаются. Совпадающие находки правил и модели объединяются (источник `rule+llm`).

Такой гибрид даёт воспроизводимость (ядро детерминировано, повторные прогоны дают тот же набор очевидных нарушений) и глубину (модель видит семантику). Требование ИБ-06 проверяется полностью без модели.

## 3. Полнота анализа (ТЗ 4.4.4)

- **Проект целиком, а не diff.** Триггер — push, но агент всегда индексирует все файлы рабочей копии (в отчёте — число файлов по категориям). Изменённые файлы коммита вообще не используются.
- **Индексирование.** Сквозные требования (ИБ-01, 02, 07, частично 04 и 08) проверяются по полному перечню маршрутов, моделей и подключений сигналов: например, для ИБ-07 правило проходит все маршруты чтения и сверяет их с механизмами журналирования, а не ищет `audit` в одном файле.
- **Предварительный отбор файлов по требованию.** Для каждого требования — свой набор шаблонов путей (settings/urls — всегда; views/access — для ИБ-01/02/08; audit/acl/collector — для ИБ-05/07; models/hashers/storage — для ИБ-04; json/serve — для ИБ-03). Библиотечный форк `src/helpdesk` включается, только если его код реально подключён к маршрутам проекта (ТС 4.1.5).
- **Бюджет контекста.** Исходники добавляются по приоритету до бюджета (по умолчанию 240 тыс. символов ≈ 60–80 тыс. токенов на вызов); крупные файлы усекаются с пометкой. Не вошедшие файлы перечисляются модели, и она может запросить их через `need_files` — второй раунд с расширенным бюджетом.
- **Поэтапная обработка и агрегация.** Индекс → правила → модель по каждому требованию (до 3 параллельно) → объединение, дедупликация по месту, статус по каждому из 8 требований, включая «соответствует» и «недостаточно данных».
- **Время.** Внутренний дедлайн 25 минут (job — 30). Требования, не успевшие к модели, получают статус `not_checked` с сохранением находок правил — отчёт формируется в объёме выполненного.

## 4. Обработка ошибок

- Недоступность модели, 429/5xx после 3 повторов с экспоненциальной паузой, нет ключа или адреса API → код 2, отчёт не формируется (ТЗ 4.7.3), в журнале — `::error::` с причиной.
- Пустой, обрезанный или не-JSON ответ модели → один повтор со строгой инструкцией «только JSON» (при `finish_reason=length` — с вдвое меньшим объёмом исходников). Если и повтор непригоден: при находках правил статус «нарушено» по правилам + `analysis_warning`, без находок — «недостаточно данных»; в обоих случаях запись в «Ограничения» и `::warning::` в журнале шага. Для каждого вызова в отчёт пишутся `finish_reason`, токены и длина ответа.
- Статус ответа модели принимается только точным `pass` / `violation` / `insufficient_data`; любой другой или отсутствующий никогда не становится «соответствует» — это «недостаточно данных» (или `analysis_warning` при подтверждённых правилами нарушениях).
- «Недостаточно данных» не блокирует пайплайн сам по себе: по ТЗ 4.3.6 и таблице соответствия кода и `overall_result` код 1 — только при нарушениях; такие требования видны в отчёте, в «Ограничениях» и в журнале шага (флаги `--fail-on-insufficient` / `--fail-on-incomplete` есть, но в workflow не включены).
- Ошибка отдельного правила не роняет проверку — фиксируется в разделе «Ограничения».

## 5. Известные ограничения

- Индексатор рассчитан на Django-проекты (urls.py, settings.py, модели ORM); для других фреймворков остаются инвентарь, текстовые правила и анализ моделью.
- Динамически формируемые маршруты и настройки (вычисляемые в runtime) статически не раскрываются — отмечаются в заметках индекса.
- Шифрование полей ПД определяется по типам полей и движку БД: шифрование, реализованное нестандартно (например, в `save()`), правило может не распознать — такая находка помечается «вероятно» и может быть снята моделью с контрдоказательством.
- Права доступа к файлам (ACL Windows) оцениваются по коду их настройки, а не по фактическому состоянию сервера.
- Каталоги `agent/` и `.claude/` и собственный workflow агента `.github/workflows/ib-check.yml` исключаются из анализа как принадлежащие агенту; одноимённые каталоги проверяемого проекта также будут пропущены, а `.py`-файлы внутри `.github/` не сканируются (workflow-файлы проекта при этом остаются в инвентаре и учитываются для ИБ-03).
- Путь с моделью проверен двумя реальными прогонами (см. п. 1), итоговым — после исправления; разброс результатов модели между прогонами (состав её находок, число токенов) систематически не измерялся. Работа с Qwen реализована, но на живом API не проверялась.
- Требование со статусом `insufficient_data` не блокирует пайплайн само по себе — код завершения 1 дают только фактические нарушения. Это сознательное решение по прочтению ТЗ §4.3.6 («не блокировать пайплайн при отсутствии нарушений») и требования соответствия кода завершения полю `overall_result`: статус «недостаточно данных» виден в отчёте, в разделе «Ограничения» и предупреждением в журнале шага, но на код завершения не влияет.
- Если модель не дала пригодного ответа и после повтора, требование оценивается только правилами — глубина анализа по нему ниже (это явно отмечается в «Ограничениях»).
- Качество семантической части зависит от модели; её ответы проверяются по месту в коде, но не могут быть полностью детерминированы.
- Исходный код проверяемого проекта передаётся провайдеру модели (допустимость — решение организатора, ТЗ 4.9.2); режим `--provider none` работает без передачи.
